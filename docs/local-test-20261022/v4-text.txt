[/body/p[@paraId=1E2B5C9E]] 三 系统设计与持久化
[/body/p[@paraId=008CEA2D]] 3.1 应用结构
[/body/p[@paraId=39006C7B]] 浏览器通过 Vue3 页面操作游戏，Spring Boot 提供牌局、翻牌、暂停、成绩提交和排行榜接口。前端构建结果复制到后端静态资源目录，再打入可执行 JAR，因此一个应用容器即可同时提供页面和接口。
[/body/p[@paraId=604E83FF]] 游戏提供轻松 6 对、标准 8 对和挑战 12 对三种难度。后端随机生成卡牌顺序并判断配对，负责步数和计时。未翻开的答案不会直接传给浏览器；暂停时保留本局状态并停止计时，恢复后继续游戏。
[/body/p[@paraId=3F2AC6B9]] 3.2 SQLite 数据设计
[/body/tbl[3]] [Table: 5 rows]
[/body/p[@paraId=46990D47]] 运行中的牌局保存在服务端内存中；服务重启后需要重新开局。已提交成绩保存在 SQLite 数据库，排行榜按步数升序排列，步数相同再比较用时。持久化对象是已保存成绩，不包括未完成牌局。
[/body/p[@paraId=789F2F70]] 3.3 容器数据卷
[/body/p[@paraId=0DEBC2F1]] volumes:
[/body/p[@paraId=28A256B8]]   - garden-data:/app/data
[/body/p[@paraId=76E58909]] # 命名数据卷的实际名称
[/body/p[@paraId=5EC72750]] name: memory-game6085-data
[/body/p[@paraId=193C0A72]] 镜像保存应用程序，数据库由运行时生成并写入 /app/data。该目录挂载到命名数据卷后，删除应用容器不会自动删除成绩文件。实验重建容器时继续挂载同一数据卷，以验证程序与数据的生命周期可以分离。

[/body/p[@paraId=0413DDE8]] 8.1 启动与端口问题
[/body/p[@paraId=0934D238]] Docker Desktop 最初因遗留 socket 无法访问而退出。原运行时目录改名被 Windows 拒绝，最终通过仅为 Docker Desktop 子进程设置独立运行时缓存目录恢复启动，系统级环境变量未修改。恢复后以 Client 与 Server 响应以及实际容器结果验证环境可用。
[/body/p[@paraId=4A716604]] 首次构建遇到基础镜像下载中断；重新拉取所需基础镜像后完成构建。现有课堂项目占用 8080，因此将本实验宿主机端口调整为 18085，同时保留容器内部端口 8080。
[/body/p[@paraId=7B637FB7]] 8.2 实验总结
[/body/p[@paraId=33278EA3]] 本实验完成了应用打包、镜像构建、容器访问、镜像发布与拉取，以及数据卷跨容器保留的完整验证。镜像用于分发应用程序，容器是运行实例，Registry 用于保存和分发镜像，数据卷用于保存独立于容器生命周期的数据库文件。
[/body/p[@paraId=0F97C023]] 重建前后容器标识发生变化，但保存的成绩没有变化，说明 SQLite 文件与应用容器已经通过命名数据卷实现生命周期分离。后续复现实验时，应保持仓库地址、镜像版本、应用端口和数据卷名称一致。
