[/body/p[@paraId=1EF0E0FA]] 三 系统设计与持久化
[/body/p[@paraId=19F3A56C]] 3.1 应用结构
[/body/p[@paraId=331DE877]] 浏览器通过 Vue3 页面操作游戏，Spring Boot 提供牌局、翻牌、暂停、成绩提交和排行榜接口。前端构建结果复制到后端静态资源目录，再打入可执行 JAR，因此一个应用容器即可同时提供页面和接口。
[/body/p[@paraId=1D6BFAF8]] 游戏提供轻松 6 对、标准 8 对和挑战 12 对三种难度。后端随机生成卡牌顺序并判断配对，负责步数和计时。未翻开的答案不会直接传给浏览器；暂停时保留本局状态并停止计时，恢复后继续游戏。
[/body/p[@paraId=5287B87C]] 3.2 SQLite 数据设计
[/body/tbl[3]] [Table: 5 rows]
[/body/p[@paraId=2A2A9FB6]] 运行中的牌局保存在服务端内存中；服务重启后需要重新开局。已提交成绩保存在 SQLite 数据库，排行榜按步数升序排列，步数相同再比较用时。持久化对象是已保存成绩，不包括未完成牌局。

[/body/p[@paraId=59081E06]] name: memory-game6085-data
[/body/p[@paraId=2774A1C0]] 镜像保存应用程序，数据库由运行时生成并写入 /app/data。该目录挂载到命名数据卷后，删除应用容器不会自动删除成绩文件。重建容器时继续挂载同一数据卷，检查已保存的成绩是否仍可读取。

[/body/p[@paraId=754E169C]] 8.1 启动与端口问题
[/body/p[@paraId=4FC6640B]] Docker Desktop 最初因遗留 socket 无法访问而退出。原运行时目录改名被 Windows 拒绝，最终通过仅为 Docker Desktop 子进程设置独立运行时缓存目录恢复启动，系统级环境变量未修改。恢复后，Client 与 Server 均能响应，容器也可正常运行。
[/body/p[@paraId=08F8E021]] 首次构建遇到基础镜像下载中断；重新拉取所需基础镜像后完成构建。现有课堂项目占用 8080，因此将本实验宿主机端口调整为 18085，同时保留容器内部端口 8080。
[/body/p[@paraId=4EBAF534]] 8.2 实验总结
[/body/p[@paraId=755DB3F7]] 本实验将 Spring Boot 项目打包为镜像，推送到本机 Registry，并在删除本地应用镜像标签后重新拉取。使用拉取的镜像创建新容器后，页面和接口可正常访问。
[/body/p[@paraId=26CDF009]] 重建前后，容器标识发生变化，已保存的成绩保持不变，说明容器重建后仍能读取原数据卷中的 SQLite 数据。后续复现实验时，应保持仓库地址、镜像版本、应用端口和数据卷名称一致。
